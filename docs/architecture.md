# Architecture

Lacquer is a modular monorepo, with three processes rather than distributed business microservices. The initial product is nail-salon-first, while foundation entities use general names so other beauty businesses can be introduced without renaming identity and tenant infrastructure.

```text
Browser -> SvelteKit same-origin proxy -> Fastify -> PostgreSQL
                                             -> Redis (throttling)
Development producer -> Redis BullMQ queue -> Worker
```

The web proxy forwards only selected headers and a fixed upstream URL; it does not authenticate or authorize users. It forwards Set-Cookie without exposing cookies to JavaScript. Requests to the API receive the same enforcement whether they originate from the web or another client.

## Ownership and dependencies

- `types`: centralized fixed roles and permission policy. No framework dependencies.
- `schemas`: Zod contracts with inferred transport types; depends on types.
- `db`: database client, schema, migrations, seed and tenant predicates; depends on shared contracts.
- `api`: authentication, tenant context, permission enforcement and domain services.
- `web`: UI state and transport; imports shared contracts and components.
- `worker`: a registry dispatches the one development job. No business jobs exist.
- `booking-engine`: reserved for pure TypeScript domain rules; no UI or provider imports.
- `integrations`: reserved for email/SMS, Stripe, Square, and Google Calendar adapters.

## Database

All entity identifiers are UUIDs generated by PostgreSQL. Timestamps use `timestamptz`; updatedAt is refreshed by Drizzle updates, not by a database trigger. Raw SQL maintenance must update it explicitly.

| Table                  | Ownership / constraints                                                                               |
| ---------------------- | ----------------------------------------------------------------------------------------------------- |
| users                  | Installation-wide; unique normalized email, optional password hash for future passwordless identities |
| tenants                | Unique slug, active/suspended status                                                                  |
| tenant_memberships     | Tenant/user foreign keys; unique pair; fixed role enum                                                |
| membership_permissions | Membership FK; composite key (membership, permission); explicit allow/deny                            |
| locations              | Tenant FK; unique (tenant, slug); address, timezone, active flag                                      |
| sessions               | User FK; unique token hash, expiry index, expiry-after-creation constraint                            |
| auth_tokens            | User FK; purpose enum, unique token hash, expiry index and constraint                                 |

Owner membership creation and tenant creation are atomic. A user can own or join several salons. No single tenantId is stored on users. The seed demonstrates two memberships per user. Future tenant-owned entities must have tenantId and use composite tenant/resource foreign keys when referencing other tenant-owned entities. This prevents a future appointment, for example, from pointing to a location in a different tenant.

Installation configuration lives in typed environment variables rather than an installation row. Currency is installation-wide; timezone is per location. No future business settings are stored prematurely. Postgres enums and foreign keys make invalid roles and orphan records impossible.

## Request lifecycle

1. Structured request logging with generated request IDs; bodies, cookies, and query strings omitted.
2. Redis-backed rate limiting and origin/custom-header checks for mutations.
3. Shared Zod request validation, including UUIDs, strict object fields, slugs and IANA timezones.
4. Authentication by a hashed, unexpired, revocable session.
5. Active tenant resolved from the route only after querying the authenticated user's membership and tenant status.
6. Effective permission computed from fixed role plus per-membership toggles. Owners retain all permissions.
7. Service executes a tenant-scoped query; location resource IDs are never queried alone.
8. Shared response schema validates the safe public projection. Database dates become ISO strings.

For this milestone every active member can read tenant/location basics. Mutations require manage_business or manage_locations. There are no membership or toggle mutation endpoints yet. New route authors must use guards and services rather than querying the database directly.

## Runtime

`/health` checks the HTTP process; `/ready` checks PostgreSQL and Redis. Worker exposes these routes on port 3002; readiness reflects Redis connection and worker lifecycle. SIGINT/SIGTERM close HTTP, workers, and owned connections with a deadline. Queue shutdown waits for in-flight work; Redis is configured with noeviction in Compose.

Service worker caching is restricted to public build/static assets. Navigations and API responses remain network-only. The manifest includes generated placeholder PNG/SVG icons and standalone display; HTTPS or localhost is required for browser installation. Branding and offline workflows are deferred.

OpenAPI is generated through the Fastify Zod type provider and @fastify/swagger. Drizzle migrations are generated and committed with their snapshots/journal. See the upstream [Fastify type-provider documentation](https://fastify.dev/docs/latest/Reference/Type-Providers/) and [Drizzle migration generation documentation](https://orm.drizzle.team/docs/drizzle-kit-generate).
